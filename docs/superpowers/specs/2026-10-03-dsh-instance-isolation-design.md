# 鲸域：DSH 全形态独立实例设计

日期：2026-10-03

状态：方案方向已获用户同意；本书面设计等待审阅。尚未进入产品代码实现。

## 1. 用户目标与成功条件

用户明确要求：官方桌面版、社区桌面版、官方网页版均为单独个体，隔离部署与启动，不影响电脑上的其他 DSH。

创建成功必须同时满足：

1. 从下载、部署、自检到首次运行均不改写已有 DSH 的程序、数据、卸载记录、快捷方式、协议关联、CLI/PATH 或配置。
2. 两个鲸域实例拥有不同的可写运行体副本、数据目录、桌面壳配置、工作区、缓存、访问会话、端口和进程归属。
3. 启动、停止、暂停、重启、删除、恢复一个实例不影响另一个实例或鲸域之外的 DSH。
4. 只有实际通过部署与隔离自检后才返回成功并显示为可运行实例。
5. 网络、解包、自检、登记任一步失败，不破坏原目录或其他任务，只清理本任务拥有的临时文件。

独立实例表示正确的应用状态和生命周期隔离，不表示不同 Windows 用户权限或对恶意运行体的操作系统安全沙箱。

## 2. 现状与根因

- `hub/electron/create-runtime.ts` 在社区版本收录阶段执行普通安装器 `/S /D=...`；之后才判定能否托管。
- 普通安装器可以根据固定应用身份查找旧安装、执行旧卸载、写入登记与快捷方式；不同安装目录不能消除这些副作用。
- 官方 Web 已有便携 Node、npm 部署和服务自检，不需要重新从零开发。
- 本地官方 Desktop 有 userData 与端口补丁，不能把该版本的能力推定为任意官方安装包的能力。
- 社区 Desktop 的核心数据目录与桌面壳存储、CLI 集成、更新器等必须分别检查。
- 当前创建目标目录清理、注册表写入、停止等待与状态同步不足以承诺完整独立性。

## 3. 总体方案

采用“可信资产目录 + 免安装运行体 + 发行体适配器 + 统一实例事务与生命周期”。

不在用户主机执行 DSH 普通安装器。不能安全取得免安装载荷的版本，采用允许修改和再分发的源码构建适配运行体；构建产物注明来源、版本、补丁与许可证。

三种形态都是最终交付目标。支持以版本和运行体能力为单位认证：不能宣称任意上游版本天然支持隔离，也不能通过仅禁用桌面创建而宣称本项目已完成。尚未适配的版本展示准确说明，不允许进入有副作用的安装路径。

## 4. 可信版本目录与适配契约

主进程从受信来源解析版本与资产，保存资产标识、上游版本、来源、类型、平台、完整性依据和适配器版本。渲染层仅选择标识，不指定要执行的下载 URL 或本地文件。

每个适配器负责：

- 验证资产、解包布局与真实运行体版本；拒绝路径逃逸、链接逃逸和非预期载荷。
- 声明并实现数据、壳配置、端口、单实例与运行体更新行为的隔离。
- 产生启动规格和健康检查条件，提供退出、崩溃与进程归属事件。
- 明确哪些文件由运行体写入，禁止引用其他实例的可写状态。

只有符合完整契约的版本成为可创建版本。上游 latest 指针不可当作任意历史版本的精确安装资产。

## 5. 三类运行体

### 官方 Web

保留便携 Node 与指定版本 DSH 的独立部署，npm 缓存及安装环境位于实例内，不使用全局 npm 安装。隔离环境在依赖安装与自检前建立；审查安装脚本的副作用并限定批准构建步骤。

运行时显式设置独立 DSH_HOME、工作目录、loopback 地址与端口，禁止运行体自行打开默认浏览器。使用真实服务就绪条件并验证服务进程归属。

访问界面使用无 Node 权限、独立持久化 partition 的 Electron Web 窗口，不将多个实例的登录存储与普通浏览器 cookie 共用。窗口仅加载该实例本地服务，外部链接交给系统浏览器；不注入 Hub 的管理 preload。

### 官方 Desktop

运行体作为完整免安装文件树部署到实例，不创建系统安装记录。

对每个支持版本核验或应用适配：在单实例锁申请之前设置独立 Electron userData；主进程、宿主及服务采用独立 DSH_HOME、工作区与端口；默认更新器、协议注册或其他整机行为关闭或改为实例范围。

本地已有补丁运行体用于开发验证。正式发行的源码提交、补丁、构建脚本、完整性与获取方式均需可追踪，不依赖开发机 D 盘路径。

### 社区 Desktop

优先适配已选 dsh-tauri 发行体，审查并修改桌面壳路径、WebView 存储、单实例插件、端口、CLI/shim、协议和更新器行为。DSH_HOME 被核心读取不等于全部隔离通过。

需要源码构建时使用明确版本和独立受管壳身份，运行时依照实例标识选择存储与锁。关闭默认全局 CLI 注册与系统快捷方式修改。免安装包仍需验证这些运行时行为。

不能将社区运行体悄悄替换成官方 Web 并继续标注为社区桌面版。

## 6. 实例布局与事务

逻辑布局：

```text
用户选择的实例目录/
  instance.json       # 实例标识、所有权与适配信息
  runtime/            # 该实例完整运行体副本
  state/              # DSH 与桌面壳状态、浏览会话
  workspace/
  cache/
  logs/
  mirror/
  mirror-history/
```

已有实例继续使用现有路径记录，不自动迁移或移动用户数据。新实例路径模型与旧记录兼容；注册表保留解析后的明确路径，业务不能隐式假设所有实例都在开发工作区。

创建前验证目标真实路径、现有实例关系、目录为空、可写空间及任务互斥。临时部署使用同卷独占 staging 目录及所有权标记。

下载与自检完成后再次核验目标仍未被其他操作占用，发布文件树并串行登记。登记失败按任务所有权回滚；若回滚失败，明确返回残留位置及失败原因。不得静默吞错或递归清理后来出现的用户文件。

重启可识别未完成任务并提示恢复/清理；不自动删除无所有权证据的目录。

## 7. 统一生命周期

每个实例串行处理生命周期命令，同时不同实例可并行运行。

启动期间支持取消；服务就绪后才能标记 ready。所有实际 runner 纳入监督，退出与崩溃及时清除运行标记。

停止先请求退出，再等待真实进程树结束，超时只处理该实例已登记并核对身份的进程。禁止按程序名批量结束其他 DSH，禁止强行释放被外部实例占用的端口。

端口在创建与每次启动时检查注册保留和实际占用，串行预留；运行体占用失败后明确重试或失败，不抢占已有服务。

只有实际停止后才允许快照、恢复或删除。快照各根目录使用独立命名空间，通过临时镜像发布；失败保留旧基线，恢复错误真实返回。

## 8. 用户界面与配套

保留用户指定名称、目录、类型和版本的交互及现有工具栏顺序。创建中固定表单并防重复提交，窗口关闭不产生无主任务；进度属于明确任务并显示真实阶段和错误。

三类状态、支持版本和未适配原因使用准确文案。主界面搜索、使用引导、详情、全部现有九种语言及中英文内置手册同步。

## 9. 开源与发行

- 不修改现有 GPL 正式全文；新增自有源码保留项目版权头。
- 从锁文件生成完整依赖清单，区分随包分发、构建开发、按需下载；核对实际版权和许可文本，软件内展示与发行包同源。
- 对 source-lock 记录的 fork base 核对实际沿用文件及授权，不能以添加致谢替代授权依据。缺少依据的内容需取得许可或替换。
- 保存适配运行体的上游来源、许可证、补丁和对应源码构建方式。
- 仓库账号由用户提供，不能猜测身份；本地配置支持未设置状态。公开推送与 Releases 上传在文件、来源和测试准备好后进行。
- 补充 NSIS 与完整 zip 双产物；稳定可写数据根目录位于程序目录之外，保留现有 userData 包名和设置。
- 更新仅替换鲸域程序，不替换各 DSH 实例状态。可信产物校验与安装结果确认先于接通真实自动更新。

## 10. 验收与保护边界

自动回归覆盖：普通安装器零执行；伪造资产拒绝；目录与链接逃逸拒绝；并发创建；每阶段失败及回滚；同名文件镜像比较；注册表并发；启动取消与实际退出；端口冲突；旧记录兼容。

运行验收在专门测试实例与可恢复环境中完成：

1. 各类分别创建两个实例并行运行，检查数据、壳状态、服务及进程归属。
2. 修改 A 的配置、会话与文件，B 保持原状态。
3. 停止、重启、删除或恢复 A，B 的服务与数据保持不变。
4. 比较部署前后相关系统登记、快捷方式与已有 DSH 状态，确认未被改写。
5. 创建失败后原目标及外部 DSH 保持原状态；软件不得显示成功。
6. 干净 Windows 安装与 zip 首次运行均能取得受信适配运行体，不依赖本机绝对路径。

当前 3080 实例、<user-profile>\\.dsh 和 D:\\DSH-Desktop 不作为试装、自检、恢复或修改目标。已有未跟踪 backup-dsh-home.ps1 保留。

静态检查和单元测试通过不等于完成运行验收；未验收版本不写成已支持。三种形态全部完成适配和上述验收后，才能宣称主体目标完成。

## 11. 实施分段

第一段：在主进程阻断普通 DSH 安装器执行，建立可信创建请求、任务目录和事务回滚，并保持官方 Web 业务可用。

第二段：统一实例路径、生命周期、端口、登记和镜像的独立性保障，完成 Web 独立浏览会话。

第三段：完成官方 Desktop 和社区 Desktop 的免安装适配、可追踪构建与版本认证，不因临时阻断而结束任务。

第四段：补全许可来源核对、完整依赖与声明、语言与文档、双发行包和仓库/更新配置，完成实际验收。

下一阶段为书面设计审阅；通过后编写按以上分段组织的实现计划。
